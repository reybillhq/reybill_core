# ReyBill white-label audit — v1.0.0 stable base

Audit date: 2026-10-04. Site: `reybill.localhost`. Installed source: Frappe 16.36.1 and ERPNext 16.37.0.

## v1.0.0 release addendum

The approved current base reports **ReyBill Core 1.0.0** in the ReyBill-owned
About dialog. Package versioning also updates owned branding asset cache keys.
The Desk logo now uses the approved `.navbar-home img` 150px height and automatic
width rule; native navbar height and existing black/white theme switching remain
intact. The known 390px Search wrapping and 390px/430px transparent logo overlap
are preserved and recorded in the [release validation](validation/v1.0.0/RELEASE_VALIDATION.md).
Saved Desktop layouts are neither reset nor modified for this release.

The inventories and v0.0.4 findings below remain historical evidence. Outstanding
customer surfaces and classifications are unchanged; promotion to a stable base
does not authorize further white-label changes. In particular, the authenticator
issuer remains **Frappe Framework — NEEDS REVIEW**.

## Scope and evidence (historical v0.0.4)

This is an inventory, not authorization to implement all remaining surfaces. The v0.0.2 and v0.0.3 milestones supplied Desktop/menu naming, CRM sidebar presentation, removal of the external CRM promotion, and a ReyBill-owned About dialog. The approved v0.0.4 milestone adds native authentication-screen branding, a ReyBill favicon, display app names and an official animated SVG splash with static fallback. Website Settings' `app_name`, `app_logo`, `favicon`, `splash_image`, and System Settings' display `app_name` are persistently updated. The explicitly approved Desktop addition sets native icon/layout indices, Home/CRM/Support default visibility and the removed ReyBill record's artwork URL; all other record fields remain intact. Core source, Workspace/Navbar records, app metadata, authentication configuration, workflows, permissions and routes remain untouched. The final navbar logo uses native Frappe sizing with ReyBill source switching only. No general color/layout redesign or animation dependency is included. ReyBill Core reports version 0.0.4.

The original source-scan inventory covers both installed repositories, including templates, Python, JavaScript, JSON, development examples and localization catalogs. It searches `Frappe`, `Frappe Framework`, `Frappe Support`, `ERPNext`, and vendor URLs. It excludes Git internals, dependencies, generated bundles/source maps, ignored files and binary assets. The CSV snapshots retain their historical classifications; the surface tables below record subsequent implementations and discoveries. Image branding is inspected separately through configured asset paths and browser screenshots.

[WHITE_LABEL_SOURCE_INVENTORY.csv](WHITE_LABEL_SOURCE_INVENTORY.csv) contains every matching source line from that scan, with its path, line number, matched terms, classification and rationale. There are 10,092 matching lines: 21 **SAFE TO WHITE-LABEL**, 5,614 **INTERNAL — DO NOT TOUCH**, and 4,457 **NEEDS REVIEW**. The line classifications are conservative: untranslated catalog entries, unfamiliar messages, external-service names and vendor links remain review candidates rather than being assumed safe. A line may contain multiple occurrences; the inventory groups these at their source location. It does not copy full source lines or credentials.

Lowercase Python imports, app IDs, database names, asset namespaces, routes and API paths are technical identifiers, regardless of whether a textual scan matches them. The inventory does not authorize renaming them. A safe visible caption and an internal record key can have identical text; only the rendered caption is a white-label candidate.

The live database inspection covered 35 Desktop Icons, 19 Workspaces, 32 Workspace Sidebars, 5 Navbar Items, 13,760 DocFields, 43 Print Formats, 1 Email Template, 4 Notifications, 1 Website Theme, and the Website/System/Navbar settings. There were no Web Page or Letter Head records. Sent emails, historical notification logs, transaction contents, attachments and generated historical PDFs were not inspected. Their branding can depend on user-authored content and cannot be inferred from current templates alone.

[WHITE_LABEL_SITE_INVENTORY.csv](WHITE_LABEL_SITE_INVENTORY.csv) identifies 32 matched site field entries, including the Framework caption and the two application-name settings. Entries record brand terms and schema/record references, not account secrets or email bodies.

The CSV inventories are the original v0.0.2 scan snapshots. The tables below add the current milestone's findings and approved presentation decisions; the source inventories do not imply that upstream files were edited. Runtime installed app IDs are still `frappe`, `erpnext`, and `reybill_core`. A separate `crm` app is not installed on this development site.

## Classification

- **SAFE TO WHITE-LABEL**: customer-facing presentation can be adapted through supported settings or app extensions while preserving its underlying identity and behavior.
- **INTERNAL — DO NOT TOUCH**: technical identity, route, relationship, source identifier, protocol, migration key, diagnostic identifier, or source attribution that must remain intact.
- **NEEDS REVIEW**: ambiguous context, third-party service identity, external destination, attribution, authentication identity, or content requiring a separate decision.

## Implementation boundaries and validation

The four Desktop mappings are merged into a copy of Desk boot's `__messages`. This is an exact-string display translation, so other Desk captions using the same complete strings inherit the naming. It does not alter substrings such as `Frappe Framework Version`, website settings, server-side `_()` translations, database labels or identifiers. Generic `About` and `Frappe Support` are not globally translated: only the requested menu models are adapted.

The Help/Navbar boot document is copied before changing its requested entries. This avoids modifying the cached standard document or causing standard item sync to create duplicate rows on migration. In this installed v16 implementation, `frappe.sessions.get()` refreshes `navbar_settings` after `extend_bootinfo` (`sessions.py:184`). The supported `update_website_context` hook therefore reapplies presentation to a copy of the final boot context only when the template is `www/desk.html`. This Desk boot adaptation does not modify website boot data. The v0.0.4 context dispatcher additionally handles only native Login, Reset Password and Complete Signup presentation. Only the standard About action `frappe.ui.toolbar.show_about()` is redirected; unrelated custom About actions remain intact. Desktop's native `desktop_screen` event is used through `page_js["desktop"]`; the adapter wraps only the emitted page instance's `setup_avatar`, then changes the current avatar menu's two item models before display. It does not replace DOM text, override the global menu factory, or edit the native About function.

The supported `app_include_js` hook loads the ReyBill dialog and Desk adapter. The native `sidebar_setup` event fires before `prepare()`, SidebarHeader construction and promotional banner rendering. The adapter wraps only that sidebar instance's `choose_app_name` and `get_crm_banner`. It keeps return values, native app selection, installed-app switch links and unrelated banners. These instance methods are installed-v16 contracts, not dedicated public per-product branding hooks; native-source regression tests and live browser checks cover their ordering and behavior. Framework upgrades require rerunning those checks.

The only runtime support destination is defined in `reybill_core/branding.py` as `SUPPORT_URL`; it is exposed through boot to the Desktop adapter, reused for equivalent Navbar Route entries, and used for the ReyBill About website link. Logo URLs and customer app captions are also centralized there. The dialog's version comes from `reybill_core.__version__`; the original `boot.versions` map is untouched. The v0.0.4 setup uses the supported Single-setting API for only the five approved display fields across Website/System Settings, and is idempotent. It deliberately avoids saving all System Settings because their validators can normalize unrelated authentication/password settings.
